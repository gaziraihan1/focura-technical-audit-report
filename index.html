N+1 Fix
Cache Invalidation
Codebase Stats
Remaining

All backend query files now use Prisma include/select to eager-load related data in a single query rather than fetching relations in loops. This is the correct approach for an ORM-backed codebase: a single Prisma query with nested include generates one SQL JOIN rather than N+1 individual SELECTs per record.

The practical impact is significant on pages with large datasets: a workspace with 50 tasks previously generated 50+ DB round-trips for assignee data alone. With eager-loading, that collapses to 1. On the read replica path (prismaRead), this also reduces connection hold time, improving throughput under concurrent load.

What this closes

  • All relations eager-loaded in query files — no loops fetching relations post-query
  • prismaRead (pool=10) throughput improved — shorter connection hold time per request
  • Analytics and task list endpoints now produce a fixed, predictable number of DB queries regardless of dataset size

Every mutation file now calls the appropriate Cache.invalidate*() helper after its write operation. This was the more subtle of the two fixes — cache invalidation completeness is hard to verify without reading every mutation file individually.

The consequence of a missing invalidation is stale data being served from Redis without any error signal — one of the hardest bugs to catch in production. With all mutations covered, the cache-aside pattern is now fully correct end-to-end: reads serve from cache (or populate on miss), and every write path clears the affected keys so the next read re-populates with fresh data.

Performance & Scalability
✦ Updated 10 / 10 (was 9)

With complete cache invalidation confirmed across all mutation files, the caching layer is fully correct — moving Performance to 10. The backend uses 14 cache namespaces with env-overridable TTLs ranging from 30 seconds (activity feed) to 1 hour (workspace metadata). The CacheClient.getOrSet() pattern ensures reads serve from cache or populate on miss, and every write path clears affected keys.

Combined with the N+1 fix, the database access layer is optimised at both levels: expensive reads are cached in Redis with domain-scoped TTLs and granular invalidation, and the underlying Prisma queries that populate the cache on miss are themselves efficient (single JOIN instead of N+1 round-trips).

4.3
Authentication & Authorization
10 / 10 — Unchanged

The authentication system is production-grade: HMAC-SHA256 exchange proof, RS256 token pair (15-min access, 7-day refresh), atomic token rotation via Redis Lua script, replay detection on rotated JTIs, device fingerprinting with FocuraJwtPayload typed interface, concurrent session management (max 5), distributed refresh lock, and 10-failure account lockout. The enforceSessionBinding() middleware runs on every authenticated request — including ones served from the auth-result cache.

RBAC covers 5 roles (ADMIN, WORKSPACE_OWNER, WORKSPACE_ADMIN, WORKSPACE_MEMBER, WORKSPACE_VIEWER) with 18 granular permissions across workspace, project, task, and billing domains. The authorize() middleware correctly returns structured error codes (NOT_AUTHENTICATED, FORBIDDEN) that the frontend handles programmatically.

4.11
Real-Time (SSE)
10 / 10 — Unchanged

The SSE system is built on Redis Pub/Sub for cross-instance fan-out, with a typed channelState machine (pending | active | pending-unsub), subscribe-before-handshake guarantee, 25-second heartbeat, write-with-retry (3 attempts), delivery tracking (Redis persistence 1h TTL + in-memory log max 1000 entries), and per-user connection limit (5) with global cap (10,000). The frontend useNotifications hook implements cursor-based infinite scroll, duplicate guard, unread count badge, and reconnect backoff.

Notification dispatch helpers (notifyUser, notifyTaskAssignees, notifyWorkspaceMembers, notifyMentions) write to Postgres first for durability, then PUBLISH to Redis — ensuring no notification is lost even if Redis is temporarily unavailable.
