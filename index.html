This is Version 2 of the Focura Technical Audit Report. Since Version 1, three significant infrastructure improvements have been implemented: Redis response caching on analytics endpoints, TanStack Query stale-time and cache-time tuning, and Redis Pub/Sub fan-out for multi-instance SSE notification streaming.

These updates directly address two of the highest-priority performance and scalability concerns from v1. The Redis Pub/Sub integration resolves the most critical architectural limitation — the inability to scale horizontally. The weighted overall score increases from 7.8 → 8.3.

2.1
Redis Pub/Sub Fan-Out for Multi-Instance SSE
✦ New SSE: 8→9

The original SSE notification stream kept an in-memory map of userId → response on each Node.js process. When horizontally scaled, a user on Instance A couldn't receive events from Instance B. This is now resolved with Redis Pub/Sub — any instance can deliver to any connected user.

Architecture Before vs After

AspectBefore (In-memory)After (Redis Pub/Sub)
Delivery mechanismres.write() directly to in-memory client mappublish() to Redis channel → subscriber on each instance → res.write() to local client
Horizontal scalingBROKEN — cross-instance delivery impossibleWORKS — any instance delivers to any connected user
Failover behaviourClient loses connection silentlyRedis re-queues; client reconnects and replays
Connection trackingMap<userId, Response> per processMap<userId, Response> per process + Redis pub/sub subscriber per channel
Dependency addedNoneioredis subscribe/publish (already in stack for rate limiting)

Redis Response Caching on Backend Endpoints
✦ New Perf: 7→9

Analytics, statistics, and storage endpoints now cache responses in Upstash Redis with a short TTL. Previously every request triggered full PostgreSQL aggregation queries. These are now served from Redis on cache hits, dramatically reducing DB load for the most expensive read paths.

Caching Strategy

Endpoint CategoryCache Key PatternBenefit
Workspace analyticsanalytics:<workspaceId>Aggregation over tasks, activities, sessions — served from Redis on repeat requests
Task statisticstask-stats:<workspaceId>Status/priority breakdowns no longer hit DB on every dashboard load
Storage usagestorage:<workspaceId>File size aggregation queries are expensive — caching reduces Supabase compute usage
Cache invalidationRedis key delete on mutationWrite paths delete cache keys so next request re-computes fresh data

Residual Gaps

  • Invalidation completeness: Confirm all write paths correctly delete their corresponding cache keys — a missed invalidation serves stale data
  • TTL calibration: Tune TTLs based on observed mutation frequency per workspace (high-activity vs. solo workspaces have very different needs)
  • Cold-start latency: First request after TTL expiry still hits the DB at full cost — consider background refresh for the most expensive analytics queries

TanStack Query staleTime / gcTime Tuning

Security Deep-Dive: SSE Token Issue
Still Open — High Priority

Flagged as High severity in v1 and not addressed in this update. GET /api/notifications/stream?token=<accessToken> exposes a 15-minute RS256 JWT in server access logs, browser history, and any monitoring tool that captures HTTP request URLs.

Recommended Fix — Short-Lived Stream Token

StepAction
1. Add endpointPOST /api/notifications/stream-token — authenticated via Bearer header, returns a one-time signed stream token valid for 30 seconds
2. Modify streamGET /api/notifications/stream?streamToken=<streamToken> — verify the short-lived token, extract userId, then discard it
3. Frontend hookuseNotifications: first call POST /stream-token to get a stream token, then open EventSource with that token
4. Expiry handlingIf EventSource closes, the hook re-requests a new stream token and reconnects — normal reconnect flow

This pattern eliminates access tokens from URLs entirely. Stream tokens are single-use, short-lived, and never appear in repeated requests.

Final Summary

This update represents a meaningful step forward in Focura's production readiness. The Redis Pub/Sub implementation is architecturally significant — most solo-built SaaS projects never consider horizontal scalability until forced by load. Implementing it proactively means Focura can scale without revisiting the real-time layer.

The two areas that most need attention now are CI/CD automation and the SSE token security issue. Without a test pipeline, cache invalidation bugs and Pub/Sub subscriber leaks will only surface in production.
